SIDECAR CONTAINER:-(Video:- https://capgemini.udemy.com/course/modern-java-development-spring-boot-microservices-spring/learn/lecture/57513237#overview)

1. A single pod can contain multiple containers.
2. One container will be the main application container and other containers will be supporting containers and they are called as sidecar containers.
3. Both containers:
Share the same Pod IP address.
Can communicate using localhost.
Can share volumes (files).
Start and stop together.
4. Common Use cases:-
Log Collection
Monitoring
Service Mesh Proxy (Istio)
Secrets Management

NOTE:- A pod can contain multiple application containers but we restrict it to have only one main application container, because if different app containers are present 
they will have different scaling requirements.

example:-
apiVersion: apps/v1
kind: Deployment
metadata:
  name: dep1
spec:
  replicas: 1
  selector:
    matchLabels:
      type: frontend
  template:
    metadata:
      name: pod
      labels:
        type: frontend
    spec:
      volumes:
      - name: vol1
        emptyDir: {}
      containers:
      - name: con1
        image: busybox
        command:
        - sh
        - -c
        - |
          while true; do
            echo "$(date) Hello World" >> /var/logs/busybox.log
            sleep 20
          done        
        volumeMounts:
        - name: vol1
          mountPath: /var/logs
      - name: con2
        image: nginx:latest
        volumeMounts:
        - name: vol1
          mountPath: /var/lib

Based on what you've described:

Nginx sidecar is probably handling TLS termination/reverse proxy.
Nginx handles the certificate (tls.crt, tls.key), performs the TLS handshake, decrypts the traffic, and forwards it to the app.
This is mainly for HTTPS requests.

Logging is likely handled by a DaemonSet (Fluent Bit, Splunk Forwarder, Azure Monitor Agent, etc.).
Monitoring is likely handled by Prometheus, Datadog, Dynatrace, or Azure Monitor agents running at cluster/node level.
