2. what happens when api-server is down? Do u like get notified?
In a well-managed Kubernetes/EKS cluster, you should get notified if the API server is down, but it depends on what monitoring and alerting has been configured.
If it becomes unavailable:
✅ Existing application pods continue running.
✅ Existing pod-to-pod communication continues working.
✅ Existing services continue routing traffic.
❌ You cannot run kubectl get pods.
❌ New pods cannot be scheduled.
❌ HPA cannot create/delete pods.
❌ Cluster Autoscaler cannot react to scaling requests.
❌ Controllers cannot reconcile desired state.
Deployments, StatefulSets, DaemonSets stop managing workloads.

3. what happens if a scheduler is down?
New pods will not be assigned on to the nodes except the pods that have nodename defined.
In this case:
Pod is created in the API Server.
Scheduler ignores it because nodeName is already set.
Kubelet on worker-node-1 sees a pod assigned to itself.
Kubelet starts the container.

NOTE:- ap-server cannot run without etcd, api gets info from etcd

2. how does ur k8s cluster actually look like in real time that u have worked, n seems like u have used eks do can u please explain in that context?
There are 3 environemnts:- dev, qa and prod. Prod and QA infrastructure must be same.
We use Amazon EKS, so the control plane (master nodes) is managed by AWS. We don't provision or maintain the master nodes ourselves. AWS runs the API server, etcd, 
scheduler, and controller manager across multiple Availability Zones for high availability.

Cluster Autoscaler and karpenter they help in scaling the nodes. They solve the same problem but in different ways:-
Cluster autosacler checks the pods that are in pending state and it will question ok the existing worker nodes cannpt allocate these pods because they have no resources left.
So it will create new node and deploy the pods on to that.
Issue:- What if pod required more cpu and memory but the node that is created by the ClusterAutosacler does not support, solution is Karpenter
NOTE:- Cluster Autoscaler and Karpenter they run as pods

Karpenter:- It checks the pod requirements and directly launces a node with higher cpu and memory. This is mostly like AWS lambda
1. Create EKS Cluster
   ↓
2. AWS creates only the control plane
   (API Server, Scheduler, etcd, Controller Manager)
   ↓
3. There are NO worker nodes yet
   ↓
4. CoreDNS, Karpenter, Metrics Server, Apps
   cannot run because pods need worker nodes
   ↓
5. All those pods stay in Pending state
   ↓
6. Create a Node Group (or some initial worker node)
   ↓
7. EC2 instances start, run bootstrap.sh,
      and automatically register with EKS
   ↓
8. Nodes become Ready
   ↓
9. Scheduler can now place CoreDNS,
      Karpenter, Metrics Server, and application pods
